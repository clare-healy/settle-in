# Settle In — Phase 1 Adversarial Review

No repository files were edited during the review itself. This file records the resulting review.

## 1. Verdicts

### YAML library — YES

Use `yaml`; do not hand-roll YAML. `docs/class-format.md § Encoding and file rules` requires duplicate-key detection, safe-schema behavior, and useful source locations, while C4 requires hostile YAML to remain inert. The library exposes a document AST, source ranges, duplicate-key errors, and alias limits—capabilities a small custom parser would have to recreate badly. However, “core schema only” is not sufficient hardening: the implementation must parse to an AST, reject tags, directives, anchors, aliases, non-string keys, multiple documents and non-finite values before conversion, and set `maxAliasCount: 0`. The library explicitly supports aliases under its defaults and documents a nonzero default alias limit. ([`yaml` documentation](https://eemeli.org/yaml/))

### `idb` wrapper — YES

Use `idb`; writing a private promise wrapper buys no product value. It closely mirrors IndexedDB and provides `tx.done`, which is the correct completion signal. This serves Principle 7 and the recovery treaty better than duplicating event plumbing. This verdict does **not** ratify the plan’s durability claim: Chrome’s current default IndexedDB durability is relaxed, so critical run transactions must request `durability: "strict"` and await transaction completion. ([`idb` documentation](https://github.com/jakearchibald/idb), [Chrome IndexedDB durability guidance](https://developer.chrome.com/blog/indexeddb-durability-mode-now-defaults-to-relaxed))

### No framework — YES

The no-framework proposal stands. `docs/implementation-treaty.md § Implementation freedom` explicitly leaves this choice open, and the live surface is a bounded state machine rather than a general application platform. A framework is not required to satisfy the screen inventory. This verdict depends on one centralized renderer/action dispatcher, deterministic focus restoration, teardown of listeners and timers, and automated accessibility/state-transition tests. Ad hoc per-screen DOM mutation would threaten Principle 5 even without violating the framework verdict.

### CI offline-emulation fidelity for A2/A3 — NO

Playwright offline mode is useful regression coverage, but it is not acceptance evidence for installed standalone Android behavior. Its documented facility changes a browser context’s network state, and its “mobile” support is emulation; neither claim establishes Pixel 6 installation, launcher cold start, Android process death, storage policy, wake lock, export behavior, or service-worker lifecycle. This is an inference from the scope of the documented facilities. ([Playwright `setOffline`](https://playwright.dev/docs/api/class-browsercontext), [Playwright mobile emulation](https://playwright.dev/docs/intro)) The counterproposal is small: CI owns cache/request-path smoke tests; a scripted physical-Pixel pass exclusively gates A1–A3 and A5 before those tests may be marked passed.

## 3. What’s missing

The plan does not name these risks as architectural obligations:

- A clock-discontinuity policy separating wall-clock display from elapsed-duration measurement.
- Strict IndexedDB durability for teaching events, plus quota, abort, blocked-upgrade and connection-termination behavior.
- A formal invariant between the event log and persisted current-state projections.
- The service-worker case where an active durable run outlives every controlled client.
- Parser resource budgets, AST feature rejection and adversarial fuzzing.
- A canonical answer for revisited-segment drift and as-taught row ordering.
- Atomic validation of hostile or future whole-library backups.
- Input serialization during slow or failed persistence.
- A boundary-content fixture for J2 and physical font-scaling work.
- A release procedure for denied persistent storage, failed backup verification and service-worker cache rollback.
- Exact 7:58/8:00 equality, reload and process-death cases.
- A physical Pixel matrix for battery saver, wake-lock denial, standalone export, launcher cold start and update-during-recovery.

No additional sound, vibration, notification, analytics, account or cloud-dependency violation was found in the proposed architecture. The plan respects those prohibitions.

No objection was found to Vite, strict TypeScript, the GitHub Pages base path, locally bundled fonts, or the stated bundle budgets. Those choices remain subordinate to production-asset and physical-device verification.

## 4. Bottom line

**M1 may not begin.**

Before code is written:

1. Record yes/no resolutions for all four triangulate nodes, including the **NO** verdict on CI fidelity.
2. Resolve the blockers concerning service-worker activation after client death, strict IndexedDB durability, device clock changes, Savasana backward events, wake-message authority, schedule-schema scope and YAML AST policy.
3. Reconcile the affected canonical documents; schema changes must update `docs/yin-flow-state-instructions.md` in the same change.
4. Amend the test gates so CI offline emulation is never reported as A1–A3/A5 acceptance, and physical Pixel 6 evidence is required.
5. Add the missing adversarial parser, actual-browser persistence, exact-time-boundary and visual-boundary cases before their corresponding milestones can be called green.

After those conditions are resolved as explicit yes/no decisions, M1 may begin with the `yaml` library, `idb`, and no UI framework.
